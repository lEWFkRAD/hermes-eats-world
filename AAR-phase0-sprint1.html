Phase 0 Spike — What We Learned

Win32 Apps — Rich Trees (T1)

  • File Explorer: 113 elements at depth 6
  • 8 unique control pattern types (invoke, text, selection, value, toggle, scroll, expand, table)
  • Full UIA automation viable for Win32 apps
  • Outlook, Notepad similarly rich

Chromium Apps — Sparse Trees (T2)

  • Edge, Chrome: render their own UI
  • Mostly PaneControl with minimal patterns
  • Chrome_WidgetWin_1 class name
  • Vision fallback essential for these targets

UWP Apps — Frame Window Problem

  • ApplicationFrameWindow hosts real content
  • Top-level search finds empty frame
  • Child windows contain actual UI tree
  • Drilling into children required for T1 access

Key Lessons Learned

What Worked

  • Adversary board review caught real issues: UWP blind spot, DPI mismatch, GetChildren hang risk
  • FP filtering eliminated 67% false positives — most adversaries applied production-grade criteria to a spike POC
  • Synthesis produced actionable, prioritized plan: 9 VALID findings mapped to P0/P1/P2/P3
  • Python pivot was the right call — uiautomation + mss proved the entire pipeline in one session
  • Modular architecture from Sprint 1 makes Sprint 2+ incremental and testable

What Didn't Work

  • C#/.NET SDK install failed in headless terminal — timeouts, GUI requirements
  • uiautomation API assumptions — SupportsPattern doesn't exist; actual API uses GetPattern(PatternId)
  • GetRootElement → GetRootControl — API naming mismatch caused runtime errors
  • DPI awareness — SetProcessDpiAwarenessContext not on all Win10; need fallback to SetProcessDpiAwareness(2)
  • find_window → TargetInfo — returns Pydantic models, not raw uiautomation controls; tree_walker needs the raw control

Open Questions

  • TargetInfo vs raw control gap — finder returns models but tree_walker needs uiautomation.Control
  • Classification thresholds — current T1/T2/T3 thresholds are spike defaults, need calibration
  • WebSocket service — Sprint 3 deliverable, no implementation yet
  • Action executors — InvokePattern, SetValue, SelectionItemPattern not yet implemented
  • WinRT Graphics Capture — should mss be replaced? Spec calls for WinRT, but mss works for MVP

Retrospective

Process & Approach Reflections

Adversary Review: High Signal, High Noise

The 4-adversary review panel was valuable — it caught all 9 VALID findings that would have been blockers in Phase 1. However, 67% of findings were false positives (mostly production-grade concerns applied to a spike POC). The FP filter + synthesis step was essential to separate signal from noise. For future spikes: consider 2 focused adversaries instead of 4 broad ones.

The C# Pivot Was a Week Saved

Attempting .NET SDK installation in a headless terminal would have consumed a full day. The Python pivot using uiautomation proved the entire pipeline in a single session. Lesson: for perception spikes, Python is the right first choice; C# sidecar is a Phase 2 concern.

API Surface Discovery Through Failure

Every uiautomation API assumption was wrong: SupportsPattern → GetPattern, GetRootElement → GetRootControl, Offscreen → IsOffscreen, mss() → MSS(). Lesson: spike code must be treated as a discovery tool, not as production-grade scaffolding.

Schema Versioning From Day One

Adding SCHEMA_VERSION="1.0.0" to the spike's JSON output was one of the highest-leverage small decisions. It means Phase 1 can evolve the schema without breaking downstream consumers. The Pydantic models make this explicit and type-safe.
